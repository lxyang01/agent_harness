# 客户反馈执行报告

## 前置条件

先确认已有足够的统计结果和证据。信息不足时补充调用 `feedback_overview`、`feedback_compare`、`feedback_anomalies` 或 `feedback_samples`，不要用空泛文字填充报告。读取具体问题样本时优先按异常结果中的 `tag` 查询；零结果时按工具 `retry_hint` 放宽一次筛选。

## 工作流

1. 写一段执行摘要，只保留最重要的变化、影响和行动方向。
2. 列出数据事实，包括范围、总量、主要问题和周期变化。
3. 按业务影响、严重程度、增长趋势和证据可信度排列问题优先级。
4. 将原因内容标记为已确认根因或待验证假设。
5. 为每个高优问题给出行动项、负责人方向、验收信号和建议时限。
6. 列出数据局限、风险和待确认事项。

## 行动项落地

当本轮提供 `work-items.prepare_issue` 和 `work-items.commit_issue` 时：

1. 先把报告结论转换成标题、完整描述、优先级和证据引用。
2. 只调用一次 `work-items.prepare_issue`，取得 `approval_id` 和待创建内容。
3. 使用原 `approval_id` 提出一次 `work-items.commit_issue` 工具调用。该调用只是执行提案，必须由 Harness Policy Gateway 在真正到达 MCP Server 前暂停并展示给用户审批。
4. 审批前不得声称工单已经创建；只有恢复后收到 `commit_issue` 的成功结果，才能报告正式工单 ID。
5. 提交失败时报告真实状态，不绕过审批，不重新创建重复请求。

## 写作要求

- 周报、月报和管理层报告必须使用可识别章节：执行摘要、数据事实、行动建议、数据局限；用户要求异常或样本时，再加入异常问题、代表性样本。
- 先结论后证据，避免直接倾倒工具 JSON。
- 每个关键数字标明范围或比较周期。
- 建议与具体问题一一对应。
- 没有负责人信息时写“建议负责人”，不要虚构姓名。
- 不以样本中的个别措辞替代统计结论。
- 反馈统计和样本只能形成“原因假设”；没有日志、实验或复现证据时，不得使用“已确认根因”。
- 报告可以独立阅读，不依赖用户查看聊天历史。

使用 [assets/report-template.md](assets/report-template.md) 作为默认输出结构，并删除没有数据支持的占位项。
