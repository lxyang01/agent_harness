# 月度守卫报告

## 前置条件

先取数再写报告：调用 `bill_overview` 获取支出结构与待核查情况，调用 `bill_anomalies` 获取四类异常清单，调用 `bill_samples` 读取脱敏样本取证；需要环比时补充 `bill_compare`。信息不足时继续查询，不要用空泛文字填充章节。读取样本时优先按异常结果中的商户或类别查询；零结果时按工具 `retry_hint` 放宽一次筛选。

## 报告结构（固定四章）

1. 支出事实：范围、总金额、笔数、类别分布、高频商户和环比变化。
2. 异常清单：按四类维度（激增、重复扣费、涨价、离群）逐项列出，附证据和置信度。
3. 根因推测：区分“已确认”与“待验证假设”，未经证实的表述遵守 root-cause-analysis 的纪律。
4. 行动计划：每项行动对应具体异常，写明动作、预期效果和建议时限。

## 行动项落地

用户直接要求"取消某订阅"或"退款"时,不要拒绝、不要建议用户自行联系客服——**发起工单就是你处理这类请求的正确方式**:调用 `work-items.prepare_issue`(标题写清目标订阅名)并继续 `commit_issue`,系统会暂停等待人工审批。工单服务未接入(工具不在列表)时,如实说明需要以 MCP 模式接入 Work Item 服务后才能发起。

当行动计划包含“取消订阅”“退款”“联系商户核实”等动作且本轮提供 `work-items.prepare_issue` 和 `work-items.commit_issue` 时：

1. 先把行动转换成标题、完整描述、优先级和证据引用。
2. 只调用一次 `work-items.prepare_issue`，取得 `approval_id` 和待创建内容。
3. 使用原 `approval_id` 提出一次 `work-items.commit_issue` 工具调用。该调用只是执行提案，必须由 Harness Policy Gateway 在真正到达 MCP Server 前暂停并展示给用户审批。
4. 审批前禁止宣称“已取消订阅”“已退款”“工单已创建”；只有恢复执行并收到 `commit_issue` 的成功结果，才能报告正式工单 ID。
5. 提交失败时报告真实状态，不绕过审批，不重新创建重复请求。

## 写作要求

- 先结论后证据，避免直接倾倒工具 JSON。
- 金额单位人民币元；每个关键数字标明范围或比较周期。
- 不展示未脱敏的交易备注。
- 建议与具体异常一一对应；没有数据支撑的行动项删除。
- 报告可以独立阅读，不依赖用户查看聊天历史。

使用 [assets/report-template.md](assets/report-template.md) 作为默认输出结构，并删除没有数据支持的占位项。
