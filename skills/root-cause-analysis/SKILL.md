# 客户反馈原因分析

## 工作流

1. 先定义待解释现象，包括时间范围、受影响模块、客户范围和异常指标。
2. 使用 `feedback_overview`、`feedback_compare` 或 `feedback_anomalies` 建立统计事实。
3. 使用 `feedback_search` 和 `feedback_samples` 获取脱敏样本，寻找重复出现的场景、错误表现和用户路径。
   - 已知分类名称时优先传 `tag`；全文检索只传可能出现在反馈原文中的短关键词。
   - 用户指定“最多 N 条”时，在查询和样本工具中显式传递 `limit <= N`。
   - 查询返回 0 条时，按照 `retry_hint` 改用标签或更短关键词重试一次；仍为空则停止推断并报告证据不足。
4. 为每个原因假设列出支持证据、反向证据、替代解释和置信度。
5. 给出能区分多个假设的验证动作，例如查询日志、版本分组、复现路径或用户回访。
6. 只有存在直接、可重复且排除主要替代解释的日志、实验或复现证据时，才使用确定性因果表述。当前反馈统计和用户样本只能支持“原因假设”，不能单独写成“已确认根因”。

## 强制区分

- 数据事实：工具结果直接支持的数量、分布、变化和样本内容。
- 分析观察：从多条证据归纳出的共同表现。
- 原因假设：尚未被系统日志或实验确认的解释。
- 已确认根因：具有直接技术证据或受控验证结果。

## 输出要求

对每个假设输出：

1. 假设内容。
2. 支持证据。
3. 反向证据或缺失信息。
4. 置信度：低、中或高。
5. 下一项验证动作。

不得用模型常识补充项目中不存在的版本、日志、接口或故障事实。完成结论前使用 [references/causality-checklist.md](references/causality-checklist.md) 自检。
